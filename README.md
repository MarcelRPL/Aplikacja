# Filler Words
### Video demo: https://youtu.be/0Wx3ykURSOA
### Description:

My project is a word game that can be played on a browser. The general idea is that 2 random letters are generated and player has to find words that fit into those generated letters, are 6 characters long, and can be found in a game dictionary. This game has two game modes - one that is playable solo and the other that pits two players against each other through online matchmaking.

In my app.py I included all the main logic for gameplay and routes. Before any of those the app has to be set up. I used Flask for the app configuration and socket.io for the online portion of the game. Besides those I also set up some global variables and functions like the set of viable words, restrictions of charachters in a password, and empty dictionaries and varibales that will be used when creating online games. Then we get to the "/index" route which passes all the required information for the generation of the friends list on the main page. The information is pulled from the game.db that will be described later in more detail. Next we have login and register routes that are making sure that all the safety meassures are in place and that account information is being saved in the database.
Then we get to the solo gameplay portion. "/solo" generates the template with 2 random letters, it also makes sure that these two letters are a viable combination and there are words in the dictionary with those requirements. "/check_word" is self explanatory - it checks if the word that player inputted is in the dictionary. "/save_game" saves all important information about the game in the database using SQLite. 
Next two routes ("/game/<int:game_id> and "/match/<int:match_id>) are responsible for generating information about the summaries of games or matches played in the past. It queries for the required information and passes it through to the frontend. "/1v1" redirects the palyer to the online match template (all of the game creation and logic is inside socket.io functions and frontend). Next we have exploration routes like "/search" that queries for the existing players based on users input and redirects to the searched players profile. "/profile/<username>" queries for all the important information about players past matches, gameplay, statistics and passes it through to the frontend. 
Following routes are about notifications and invites. "/friend_request" is a route responsible for sending a friend invite to another player, checking along the way for possible errors. "/notifications" generates all invites that are currently active for the user. "/respond_request" is an answer to the firend invite, it can either accept the invite in which case it updates the friends table in the database, or decline invite and just update the status of said invite to declined, making it inactive. "/game_invite" and "/respond_invite" do the same but with the game invitations. "/play/<room_id>" is generating "1v1.html", but for invitation games - it passes through premade room_id (which was created in "/game_invite") and changes the invite_mode to True. 
Now we reached the online portion of the code that uses socket.io. "join_game" is responsible for putting user into the designated room, setting up game data structure, starting the game, setting up timer and emitting "end_game" after the time has passed. If it's an invitation game then it checks if it's the playeer that has been invited or the player that sent an invite and either creates the room or moves the invited player into an existing room and starts the game. If it's a random matchmaking it puts the user as the global "waiting_player", if the "waiting_player" already exists it cleares "waiting_player" and moves them and the user to a new room, sets up the game data structure, starts the game, starts the timer, and emits "end_game" aftert the time has passed. "submit_word" is responsible for vetting inputted words by the users and it either rejects the word if it's invalid or accepts it. When it is accepted it gets scored. "end_game" is a function emitted by the "join_game" at the end of the timer. It is responsible for saving the results into the database, comparing those results determining the winner/loser/draw and passing important information about the match to the frontend for the summary, and in the end it clears data of the finished match from the games{} dictionary.
Next I have to events that handle connecting to the Websocket or disconnecting from it. "handle_connect" is responsible for populating the sid_user_map{} dictionary that links websocket ids with the session ids of each user who chose to play online. "handle_disconnect" does the exact opposite. It cleares the global variables that would be occupied by the waiting players, clears match data from games{} and alerts the non-disconnected player about the cancelation of a match. Also if the match has not started yet it initiates a 5 second delay on the disconnection in case it was a momentary disconnect and reconect not initiated by the invited player. It serves the purpose of handling invitations more cleanly and without bugs. 
In the end of app.py I put also a @app.conext_proccesor function called "inject_user" that simply is used to insert currently logged in users usernmae into a profile route in the layout.html.

In helpers.py I put functions responsible for opening/closing the database for quick quering and a wrap for login_required routes.

In game_logic.py I put functions responsible for some actions connected to the gameplay. "load_words" downloads valid words from a dictionary. "valid_word" checks if the word is in the dictionary, starts and end with provided letters. "calculate_score" simply calculates score based on the letters included in the word and the LETTER_POINT{} dictionary that is in the beginning of the game_logic.py. "random_letter" generates a random letter.

In game.db I store all the information about users, games, word, friends and invites. It contains 6 tables. First is called "users" and it stores each users "id", "username", and "hash". Second table is called "game" and it stores each games "id", "users_id", "opponent_id" (if it's online), "start" (start letter), "end" (end letter), "score", "mode", and "date". Next table is called "words" and it contains an "id" for each word used in a finished game, "user_id" of the user that played said word, "game_id" of the game that this word was used in, and the "word". Fourth table is called "friends" and is used to track friendslist of all the users - it has just 2 columns: "user_id" and "friend_id" to track the relationship of those two users. Fifth table is called freind_requests and it is responsible for tracking all friend invites and their status. It contains "id" for each request, "sender_id", "receiver_id", "status" (with "pending" as default), and "timestamp". And last table is called "game_invites" which is responsible for tracking all game invites and their status. It contains "id" for each invite, "sender_id", "receiver_id", "status" (with "pending" as default), and timestamp. Each time "game_id" or some variation of "user_id" is mentioned it is set as a FOREIGN KEY referencing "id" in either "game" table or "users" table.

In my styles.css I included stylization for my page. The overall theme is "chalkboard writing". To achieve this I used dark green colors, dashed lines for borders, and "Special Elite" font which looks like chalk writing. It also includes some classes specifically created to later be called in JavaScript to show a pop-up window with a summary like ".hidden" and ".modal"/".modal-content".

As for my templates I have 9 of them. One for overall layout, login page, registering page, main page, profile (logged in palyer), player profile (searched up players profile), searching page, solo game mode, and 1v1 game mode. I used JavaScript outside of gameplay mechaincs to mostly generate match histories, retrospective game summaries, friends list, notifications and errors. In 1v1.html I used JavaScript to determine if the game is an invitation or radnom matchmaking, conduct the match, generate endgame summary. I've done that by emitting different socket.io events. In solo.html I used JavaScript to conduct the gameplay and to generate the endgame summary. I decided to use JQuery for a more comfortable style of writing code and cleaner look.

In requirements.txt I included Flask - for core web framework, Flask-Session - for server-side session support, Flask-SocketIO - for realtime communication using WebSockets and Eventlet - for handling many simultanous connections efficiently. 

In folder "data" I keep the dictionary used within my game. "words.txt" contains all of the words that are potentially viable to guess in Filler Words. Durring the gameplay it gets filtered so it doesn't include words shorter than 6 letters.
